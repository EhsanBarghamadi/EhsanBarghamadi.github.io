Event Planet

یک پلتفرم مدیریت رویداد API-first ساخته‌شده با Django REST Framework: رویدادهای چندمرحله‌ای، چرخه‌ی حیات وضعیت اعتبارسنجی‌شده و attributeهای پویای type-safe.

گیت‌هابمستندات API

برگزارکننده‌ها رویدادهای چندمرحله‌ای می‌سازند و مدیریت می‌کنند؛ شرکت‌کننده‌ها رویدادهای منتشرشده را می‌بینند، ثبت‌نام می‌کنند، بازخورد می‌دهند و نتایج را می‌بینند.

پروژه فقط API است: همه‌ی تعامل از طریق endpointهای نسخه‌بندی‌شده (/api/v1/ و /api/v2/) انجام می‌شود که با OpenAPI، Swagger و Redoc و یک کالکشن Postman منتشرشده مستند شده‌اند.

کارهایی که انجام دادم

  • چرخه‌ی حیات رویداد بر پایه‌ی state machine با انتقال‌های وضعیت اعتبارسنجی‌شده که هم در ادمین Django و هم در API اعمال می‌شود
  • مدل داده‌ی EAV انعطاف‌پذیر: تعریف سراسری Attribute به‌علاوه‌ی مقدارهای هر رویداد در ستون‌های مخصوص هر نوع، تا attributeهای پویا type-safe بمانند
  • احراز هویت JWT (access، refresh و blacklist هنگام خروج) در کنار ورود مبتنی بر session برای browsable API و Swagger
  • مجوزهای مبتنی بر نقش برای برگزارکننده و شرکت‌کننده، هم در سطح permission class و هم دوباره در اعتبارسنجی serializer
  • اعتبارسنجی بازه‌ی زمانی و هم‌پوشانی مرحله‌های رویداد؛ مرحله‌ها فقط تا وقتی رویداد پیش‌نویس (draft) است قابل ویرایش‌اند
  • ثبت‌نام در سطح رویداد با اعمال ظرفیت، بازخورد فقط برای رویدادهای پایان‌یافته‌ای که کاربر در آن ثبت‌نام کرده، و نتایج منتشرشده توسط برگزارکننده
  • فیلتر بر اساس وضعیت و جست‌وجوی متنی روی عنوان و توضیحات، نسخه‌بندی API از طریق مسیر URL و مستندات تعاملی با drf-spectacular
  • راه‌اندازی با Docker Compose همراه با healthcheck برای PostgreSQL و entrypoint که منتظر دیتابیس می‌ماند و migrate اجرا می‌کند؛ تنظیمات جدا برای dev (SQLite) و prod (PostgreSQL)

تصمیم‌های طراحی

ثبت‌نام در سطح رویداد

ثبت‌نام و ظرفیت روی کل رویداد تعریف شده، نه روی مرحله‌ها. در بیشتر سناریوها — وبینارهای چندبخشی و کارگاه‌های چندجلسه‌ای — شرکت‌کننده یک بار ثبت‌نام می‌کند و در همه‌ی مرحله‌ها حضور دارد؛ پس ثبت‌نام per-stage فقط پیچیدگی اضافه می‌کرد. EventStage فقط یک واحد زمان‌بندی است.

EAV بدون JSONField

Attribute تعریف مشترک همراه با نوع داده (متن، عدد صحیح، بولین) است و EventAttributeValue مقدار را در یکی از سه ستون تایپ‌دار نگه می‌دارد. فقط یکی از آن‌ها پر می‌شود و این قانون در clean() برای ادمین و در serializer برای API بررسی می‌شود.

یک منبع واحد برای انتقال‌ها

انتقال‌های مجاز وضعیت در ALLOWED_TRANSITIONS روی خود مدل تعریف شده‌اند. Event.clean() آن‌ها را برای ادمین و EventSerializer.validate() برای API اعمال می‌کند، چون DRF به‌صورت پیش‌فرض clean() را صدا نمی‌زند.

JWT در کنار session

SimpleJWT روش اصلی برای کلاینت‌هاست؛ ورود session هم هست تا استفاده از browsable API و جریان «Authorize» در Swagger از داخل مرورگر راحت باشد.

چرخه‌ی حیات وضعیت رویداد

  • DRAFT → PUBLISHED, CANCELLED
  • PUBLISHED → ONGOING, CLOSED, CANCELLED
  • ONGOING → FINISHED, CANCELLED
  • CLOSED → FINISHED, CANCELLED
  • FINISHED → پایانی (terminal)
  • CANCELLED → پایانی (terminal)

گروه‌های API

  • عمومی — فهرست و جزئیات رویدادهای منتشرشده، مرحله‌ها و نتایج منتشرشده — بدون نیاز به احراز هویت
  • شرکت‌کننده — ثبت‌نام در رویدادهای منتشرشده، مشاهده‌ی ثبت‌نام‌های خود، ثبت و مدیریت بازخورد
  • برگزارکننده — ساخت رویداد و مرحله، مدیریت attributeهای پویا، دیدن شرکت‌کننده‌ها و بازخوردها، انتشار نتایج
  • احراز هویت — ثبت‌نام، دریافت و تمدید توکن JWT، blacklist هنگام خروج، ورود و خروج با session

تست‌نویسی

مجموعه‌ی تست‌ها با Pytest و Factory Boy نوشته شده و شامل کنترل دسترسی، مجوزها، ساخت و ویرایش، انتقال وضعیت و مرحله‌های رویداد؛ اعتبارسنجی EAV برای attributeها؛ ثبت‌نام، بازخورد و نتایج؛ و ثبت‌نام، احراز هویت و مجوزهای کاربران است. یک management command مبتنی بر factory_boy و Faker هم داده‌ی نمایشی واقع‌گرایانه تولید می‌کند.

قدم‌های بعدی

  • Throttling روی endpointهای احراز هویت و ثبت‌نام
  • کش برای endpointهای عمومی پرخوانش
  • صفحه‌بندی یکسان در همه‌ی endpointهای فهرست
  • CI با GitHub Actions برای اجرای تست‌ها و بررسی کیفیت کد
